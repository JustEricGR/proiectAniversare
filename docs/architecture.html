Aniversare Platform Architecture

Phase 2 of the roadmap: how the anniversary site becomes a platform that hosts many couples. Each couple gets its own private site, and you run the whole platform as master admin.

  • Who editsOnly the pair admin edits a pair's site. The partner views it.
  • Recipient sign-inMagic link by email. No password to remember.
  • AccountsInvite-only. Public sign-up is turned off.
  • Master adminGranted only from the Supabase SQL editor, never from a page.

Roles

A pair is one hosted site with exactly one admin and one user. A person can belong to several pairs. For example, Nadia can run her own pair where Eric is the user.

System

The app stays a set of static pages on Vercel talking to Supabase. The only new server-side piece is one Edge Function for invitations, because sending invite emails needs the service-role key.

Access rule

Every content table carries a pair_id. Two helper functions answer "is this the master?" and "what is my role in this pair?". Every policy is built from those two answers.

-- read: members of the pair, or the master
create policy read_own_pair on main_buttons for select
  using (is_master() or pair_role(pair_id) is not null);

-- write: only the pair's admin, or the master
create policy write_own_pair on main_buttons for all
  using      (is_master() or pair_role(pair_id) = 'admin')
  with check (is_master() or pair_role(pair_id) = 'admin');

-- pair_role() returns null when the pair is suspended,
-- so suspending a pair locks out its members at once

Moving the current site

Your existing site becomes pair eric-nadia. You are added as its admin and as master. Nadia is invited as its user. All existing rows get that pair's id, and photos move from git-images/ to pairs/<id>/. The old client.html link redirects to client.html?pair=eric-nadia, so the site looks the same as before.

Roadmap

Phase 1 is the current single site. Phase 2 is everything on this page, delivered in the six stages below. Phase 3 comes later.

  1. 0
    HardeningTurn off public sign-up, export today's schema and policies into the repo, confirm anonymous writes are refused.
  2. 1
    Data layerNew tables, helpers and policies; existing rows moved into pair eric-nadia. The site behaves exactly as today.
  3. 2
    Pair-scoped pages?pair= routing, magic-link sign-in for the recipient, role routing in login.html.
  4. 3
    Master consolemaster.html, the invite Edge Function, accept.html. You can create new pairs.
  5. 4
    UploadsPhoto upload in the admin panel, private bucket, signed URLs. No more GitHub step for photos.
  6. 5
    PolishPer-pair storage quotas, pair deletion with file cleanup, custom SMTP for invite emails.
Phase 3 · paid styling, later

An optional paid tier with extra built-in styling for a pair's site: themes, decorative photo frames and more page layouts. Free pairs keep today's options. Phase 2 leaves room for it with a plan field on each pair and styles chosen from data. Pricing, payment provider and the style catalogue are not decided yet.

Fix before anything else. Public sign-up is currently on for the Supabase project. If any current policy lets "any signed-in user" write, a stranger could register and edit the live site. Turning sign-up off is the first step of stage 0.
